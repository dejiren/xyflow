Code Digest: #4673 macOSスクリーンショット後のShift状態

macOSのスクリーンショット操作で欠落するShiftのkeyupを、次のpointerdownと実イベントのmodifier判定で補正し、1回目の通常ドラッグからキャンバス移動へ戻す変更。

01. 概要

macOSのCmd+Shift+3/4/5によるスクリーンショット後、ブラウザーにShiftのkeyupが届かず、Shift状態がtrueのまま残ることがある。その後にShiftを押さずドラッグすると、通常のキャンバス移動ではなく、範囲選択として解釈されるのが#4673の不具合だった。

変更の要点
  • xyflow forkの修飾キー状態を、modifierなしのpointerdownで実イベントへ再同期。
  • UserSelectionとZoomPaneが、保持stateだけでなくmousedown/mousemoveの実modifierも確認。
  • portal独自の選択オーバーレイはイベントを奪わず、Flow wrapperのcaptureで実Shift時だけ選択処理を開始。
  • 通常のShift+ドラッグ範囲選択は維持し、Shiftなしの1回目のドラッグを通常panへ戻す。
  • xyflowのsource変更を通常/ESM、CSS/nocssのdistへ反映し、portalは作業中のforkを参照。
最終修正に含めないもの

途中で調査したRedux store設定や循環参照チェックの無効化は、最終差分に含めていない。src/store/configure-store.tsは元の実装に戻っており、チェック無効化によって問題を隠す設計にはしていない。一時的なブラウザログ、Viteのデバッグendpoint、debug属性も削除済み。

変更は2つのworktreeにまたがる。共通ライブラリ側の再発防止をxyflow forkに入れ、portal側の独自overlayにも同じ入力イベントの原則を適用する構成になっている。

02. データ構造

今回増えたのはフロー定義のデータではなく、「設定値」と「DOMイベントの実値」を接続するための型・props・一時stateである。

KeyCode (例: "Shift")
        ↓ getModifierKey
ModifierKey (例: "shiftKey")
        ↓ event[selectionModifierKey]
MouseEvent / PointerEvent の実modifier

保持state                         実イベント
  selectionKeyPressed               event.shiftKey
  isShiftPressed                    event.ctrlKey / event.metaKey
        └──────────────┬──────────────┘
                       ↓
          selection開始 / 通常panの判定

追加・接続された主な型と状態:

  • ModifierKey — shiftKeyなどDOM eventのproperty名を表す型。
  • getModifierKey(keyCode) — Shift / Control / Meta / Altの設定値をDOM propertyへ変換。
  • selectionKeyCode?: KeyCode — FlowRendererからUserSelection / ZoomPaneへ渡す設定。
  • selectionKeyPressed — xyflowのuseKeyPressが保持する状態。
  • isShiftPressed / isCtrlPressed — portal独自のuseKeyboardStateが保持する状態。

03. 保管場所

永続化なし

Shift / Ctrl / Cmdの状態はReact hookのメモリ上だけに存在する。localStorage、IndexedDB、サーバーAPI、フロー定義データは変更しない。

  • 配布物: packageのmain / moduleが読む通常版・ESM版、CSS版・nocss版のdist。

04. データの流れ

BEFORE 以前
AFTER 現在

保持stateだけを信頼

Cmd+Shift+4
  → Shift keyup欠落
  → selection state = trueのまま
  → overlay / selection paneが有効
  → Shiftなしの最初のdragも
     selection扱いまたはpan拒否
  → クリックで状態が変わる
  → 2回目からpan

stateと実イベントを照合

Cmd+Shift+4後のpointerdown
  → event.shiftKey = false
  → xyflow / portal stateをfalseへ再同期
  → overlayはpointerEvents:none
  → wrapper captureもselectionを開始しない
  → UserSelectionは選択を拒否
  → ZoomPaneは通常panを許可
  → 同じ1回目のdragで移動

依存方向は片方向である。keyboard hookが状態を持ち、FlowRendererが設定を下位へ渡し、UserSelectionとZoomPaneが「保持state + 実イベント」で最終判定する。portalでは同じ原則を独自overlayにも適用する。

xyflow
  useKeyPress
    ├─ pointerdownでmodifierなしを検出 → key stateをfalse
    ├─ UserSelection → mousedown / mousemoveの実modifierを確認
    └─ ZoomPane → stale selection中のmodifierなしmousedownだけpanを許可

portal
  useKeyboardState
    └─ capture段階のpointerdownでisShiftPressed / isCtrlPressedを補正
  OperatingProcedureFlow
    ├─ overlay: 表示専用（pointerEvents:none）
    └─ wrapper onMouseDownCapture: 実Shiftありの場合だけ選択開始
